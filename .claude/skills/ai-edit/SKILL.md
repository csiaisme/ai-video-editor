# ai-edit — AI 剪輯流程

這份給 AI 讀。任何有終端機 + 檔案工具的 coding agent(Claude Code、Codex、Cursor)都能照著做。指令是純 shell,程式碼、路徑、技術名詞保留原文,說明用繁體中文。

**跟使用者說話一律用繁體中文,而且用大白話。** 使用者是不懂技術的台灣新手,他要的是「省時間、你幫他做完」。所以:
- **不丟技術名詞**:不講 EDL、render、composition、blob、LUFS、verify_cut 這些字。要提到就翻成人話(「剪點清單」「輸出影片」「對稿」)。
- **不丟工具產物給他判讀**:波形圖、逐字稿 JSON、旗標列表是你自己內部用的,不是拿給他看的。他只看「有畫面的 preview」跟「一句話的說明」。
- **你是剪接師,他是導演(而且是不懂技術、沒空的老闆)。** 交棒給他時,只給他一個清楚的 1-2-3,不是一串選項或原理。他說「好」就能往前走。

**所有路徑相對於「工具包根目錄」**(有 `setup.sh`、`tools/`、`素材庫/`、`我的影片/` 的那層,以下叫 `KIT`)。深入技術參考見 `KIT/tools/PIPELINE-NOTES.md`。

**適用範圍:** 這個流程是給「口播影片」的(有人對著鏡頭講話)。剪接靠語音逐字稿,所以沒有講話的素材(純空景配樂那種)這個流程剪不了。底層的 HyperFrames 其實能做更多類型(產品片、解說片、動態圖文等),想延伸的話用 `npx hyperframes` 直接做 — 但那不走這個技能。

「問使用者」= 用你的介面能問就問;完全自動跑的話,選合理預設並在結尾說明。

## 開場:補 PATH、檢查更新、讀偏好檔(學習循環的起點)

每次開始前做三件事:

0. **`source KIT/tools/env.sh`**。它把 `~/.local/bin` 跟剛裝好的 Homebrew 補進這個 session 的 PATH,冪等、極快。沒做這步,家目錄安裝的工具會「明明裝好了卻 command not found」(實測:安裝時寫進 `~/.zshenv` 的 PATH,當下開著的 session 吃不到 — 環境是 session 開始時快照的)。順帶看一眼 `KIT/錯誤回報/`:有沒有檔名**不是** `已送-` 開頭、也**不是隱藏檔**的報告(例如上一個 session 留下的安裝紀錄、送失敗的復盤)?有的話**照文末「回傳給課程團隊」的規則直接自動補送**(成功後加 `已送-` 前綴),不用問。

1. **檢查有沒有新版本**(只有當 `KIT/.git` 存在,也就是用 git clone 下載的才做)。跑 `git -C KIT fetch --quiet`,再看 `git -C KIT rev-list HEAD..@{u} --count`。結果 > 0 代表 Jake 出了新版 → 問使用者「有新版本,幫你更新嗎?」,說好就跑 `bash KIT/tools/update.sh`(等同 `git -C KIT pull`)。**更新完一定接著跑一次 `bash KIT/setup.sh`(Windows 用 `powershell -ExecutionPolicy Bypass -File KIT\setup.ps1`)。** `update.sh` 只拉新檔案,不會重跑安裝檢查 — 如果這次更新動到套件依賴(例如新增 opencc、換了 Whisper 後端),使用者環境不會自動跟上,一定要重跑 setup 才會裝到新套件 / 重新驗證。setup 腳本本身是冪等的(已經裝過的東西會跳過),重跑不會壞任何東西,所以**每次更新後都跑,不用另外判斷這次更新是不是牽涉依賴**。使用者的影片、素材、偏好都不會被動到(那些沒進 git)。如果不是 git 資料夾(ZIP 下載的),**跳過這步,不要報錯**。
2. **讀 `KIT/我的剪輯偏好.md`**。裡面是這位使用者過去累積的習慣(字幕風格、愛用音樂、剪接節奏等)。照著走,不要每次重問已經講過的偏好。收尾時你會更新它(見文末)。若這個檔不存在(第一次跑),從 `KIT/tools/我的剪輯偏好.範本.md` 複製一份(`setup.sh` 會自動做)。**`KIT/風格檔.json` 存在的話也一起讀** — 那是上一支簽核成品的實際參數(字型/字幕款/BGM/字卡樣式),問一句「直接沿用?」就能整組套,不逐項重問(見收尾 2.5)。**這兩份一定要讀到最後一行** — 用久了會長到幾十 KB,工具常只給你開頭一小段預覽;只看預覽就開工,會漏掉埋在後面的定案參數(實測漏過「加速 1.1 倍」跟「每支都要 b-roll」,整個特效層重算重 render)。看到被截斷就用 Read 分段讀完。

## 第一次設定 — 一次講清楚要裝什麼,再帶著裝

**大原則:使用者不開終端機。** 所有指令都是你跑;交給使用者的只有三種動作:在 Claude Code 按「允許」、在 Mac 自己跳出的視窗點按鈕或輸密碼、在瀏覽器登入。開始前先用一句話講清楚:「等下所有指令我來跑,你不用開終端機、不用打指令,偶爾按個允許或在 Mac 的視窗點一下就好。密碼只會打在 Mac 自己跳出的視窗,永遠不要打在聊天視窗給我。」把過程中發生的事(裝了什麼、卡在哪、錯誤訊息)記到 `KIT/錯誤回報/安裝紀錄-<YYYY-MM-DD>.md` — **這個檔可能已經存在**(bootstrap 前置安裝腳本會先寫一段「前置安裝」紀錄進去),存在就接著往下補,不要覆蓋,裝完照下面第 6 步整份送出。

使用者說「幫我安裝」「幫我設定」或這是第一次跑時,主動幫他把缺的東西裝好。學員是新手。這段的話術原則來自真實裝機記錄(Mac 跟 Windows 都有),照做體驗差很多:

1. **先跑檢查、彙總、一次確認**(不要每個套件分開問,新手會覺得「怎麼一直跳問題」):
   - Mac/Linux 跑 `bash setup.sh`、Windows 跑 `powershell -ExecutionPolicy Bypass -File setup.ps1`,**看 exit code**:0 = 就緒;非 0 時結尾會列「還沒完成 — 缺:…」,照那份清單補。
   - 把所有缺的東西**彙總成一句**跟使用者確認,含大小跟時間預期,例:「這台電腦缺 3 樣:Node、ffmpeg、思源宋體字型,加起來約 300-400MB、裝 10-15 分鐘,都用官方來源自動裝,要開始嗎?」
   - **要等的步驟先講要等多久**(字型 132MB、winget 下載、XXL 1.4GB 這種),不然使用者會以為當機。
2. **Mac 的安裝策略:不要幫使用者裝 Homebrew。** 這台**已經有** brew 就照用(`brew install ...`);沒有就直接走第 3 步的免密碼直裝。理由(實測,2026-07-29 Intel/Ventura 裝機記錄):Homebrew.pkg 要求 macOS 14 以上,在 macOS 13 會卡在「無法安裝在此磁碟上」這種誤導訊息;而且 Ventura 上就算裝好 brew,ffmpeg 也已無預編譯包,會從原始碼編譯數小時。免密碼直裝新舊 Mac 都通用,還不用密碼。
3. **免密碼直裝(全部裝進家目錄,永遠不需要密碼)— 沒有 brew 的 Mac 走這條主路徑:**
   - **開始前一次講清楚、一次取得同意**(不要裝到一半才冒出新的問題):「我會從三個官方/標準來源下載:Node(nodejs.org)、字型(Adobe 官方 GitHub)、影片引擎 ffmpeg(社群編譯版 — Mac 沒有官方安裝檔,這是業界標準做法,畫質跟官方完全一樣)。都裝進你的家目錄,不動系統設定、不需要密碼,OK 嗎?」同意後中途就不要再重複問。
   - Node:nodejs.org 官方 tarball → 解到 `~/.local/opt/node`,symlink 進 `~/.local/bin`。
   - 思源宋體:Adobe 官方 GitHub releases 的 `SourceHanSerif-VF.otf.ttc` → `~/Library/Fonts/`。
   - ffmpeg/ffprobe:**直接跑 `bash tools/install_ffmpeg.sh`** — 來源、版本、SHA256 都寫死在腳本裡(eugeneware/ffmpeg-static b6.1.1,arm64/x64 都有、驗過 subtitles 濾鏡),裝到 `~/.local/bin`。**不要自己另找來源**:12 台機器的安裝紀錄顯示每個 session 自己找都在踩雷(evermeet 只有 x86_64、osxexperts 的 SHA 時對時錯、martin-riedl API 已死)。**不要 `xattr -c`**:curl 下載的檔案不帶 `com.apple.quarantine`,Gatekeeper 本來就不會擋;清隔離屬性是不必要的安全弱化動作,還會被 Claude Code 的權限機制攔下、害流程卡住(實測)。
   - PATH:工具包內部用 `KIT/tools/env.sh` 就涵蓋了(setup.sh 開頭會 source),**不需要碰 `~/.zshenv`**。只有使用者自己想在終端機直接打 `ffmpeg` 才需要寫,那是選配,先問過再寫。
4. 裝完**重跑一次 setup 腳本**,確認 exit code 是 0。腳本已涵蓋各平台的安裝(Mac brew / Windows winget / 字型腳本),不用自己拼指令;腳本搞不定的例外才照 README 手動裝。
   - **然後把 `KIT/安裝完成說明.md` 的內容轉述給使用者**(setup 每次跑完會產生/更新這份)。裡面三件事都要講到:驗收訊號、接下來 3 步、以及**「資料夾裡少了幾個檔案是正常的」**。
   - **exit code 是給你判斷用的,那份說明是給使用者看的,兩件事不要混。** 實測炸過:AI 看到 exit code 0,就把結果自己改寫成一張漂亮的摘要表格,結果 setup 印的收尾訊息一個字都沒轉達 — 而 setup 剛剛用 `chflags hidden` 把 `tools/`、`setup.sh` 等 6 個項目在 Finder 藏起來了,學員打開資料夾發現檔案不見,以為裝壞了。**setup 的輸出不是只有 exit code,那段話本來就是寫給使用者的。**
5. **「pip 裝成功」不等於「能用」** — 任何用 pip/npm 裝的關鍵套件,回報「裝好了」之前要實際 import/執行一次驗證(setup 腳本對 whisper 引擎已內建這個檢查;你自己額外裝東西時也守這條)。實測教訓:Windows 上 faster-whisper pip 顯示成功、import 才爆,如果只看 pip 結果,使用者會在剪片剪到一半才發現。
6. **收安裝紀錄**:把過程紀錄(`錯誤回報/安裝紀錄-<日期>.md`)補完(結果、裝了什麼、卡過哪裡),**照文末「回傳給課程團隊」的規則直接自動送**(`type` 用 `其他`,標題寫清楚是安裝紀錄,不用問使用者)。一切順利的紀錄也要送 — 課程團隊要知道哪些機器一次過。

**這些交給使用者做(你只能引導,不能代做):** 在 Mac 自己跳出的視窗輸入密碼、點圖形安裝視窗的按鈕、在瀏覽器登入。清楚說「這步換你做:要做什麼、為什麼」,等他做完再繼續。**絕不請使用者開終端機或自己打指令** — 需要指令的一律你來跑,被權限機制擋下就請他按「允許」(先講清楚那個指令在做什麼)。

**碰到安全性防護擋路時(例:Windows Smart App Control 擋 faster-whisper)**:絕不代替使用者關閉系統安全設定 — Smart App Control 一關就要重灌才開得回來。話術先講人話再給選項,不要丟術語:「有個 Windows 內建的安全防護擋住一步。這個防護不建議關(關了要重灌才能開回來),所以我不會動它。你可以選:(A) 等幾小時或重開機再試一次,這個封鎖常會自己解除 (B) 換一個不會被擋的替代方案(要多下載 1.4GB) (C) 先跳過,其他功能照常用。」

**底線:** Claude Code 本身的安裝跟登入是在這個技能能跑之前就完成的(不然使用者沒辦法跟你講話)。永遠不要嘗試從這裡安裝 Claude Code。

**轉逐字稿是跨平台的。** `transcribe.py` 會自動判斷後端:Apple Silicon 用 `mlx-whisper`(最快),Intel Mac／Linux 用 `faster-whisper`,Windows 用 `faster-whisper-xxl` 獨立版(pip 版 faster-whisper 在 Windows 會被 Smart App Control 擋,獨立 exe 不會)。同樣的模型、同樣會有重複字出錯的問題,所以下面的 xref／波形驗證步驟三邊都一樣重要。Windows 的 XXL 產出是簡體,`transcribe.py` 已內建 OpenCC 自動轉繁,不用你處理。若 Windows 使用者的逐字稿引擎沒就緒(exe 沒放好),`transcribe.py` 會直接報錯並指到下載位置 — 照 README「Windows 疑難排解」引導他放好 `tools/whisper-xxl/`。Windows 的一鍵安裝是 `setup.ps1`(PowerShell),不是 setup.sh。

設定好之後,下面簡寫:`PY="$KIT/tools/freecut/.venv/bin/python3"`、`H="$KIT/tools/freecut/helpers"`。

## 資料夾結構與清理 — 幫新手保持整齊

**一支影片一個資料夾**,放在 `KIT/我的影片/` 底下。使用者開始時,建好這個結構並用一句話跟他說明:

```
KIT/我的影片/<專案名>/
  <原始影片檔>        原檔,絕不動它
  成品.mp4            完成的影片 — 他要的就這一個
  審片區/             審片窗口:開始審片.html(影片+字幕已內嵌),由你幫他打開,他不用自己找
  工作檔/             其他全部丟這(使用者平常不用開):
    transcripts/       逐字稿 JSON + <名稱>.words.txt(compact,讀這份)
    edl.json           剪接配方(唯一真相)
    preview_v*.mp4     預覽(舊的邊做邊刪,只留最新)
    captions/          字幕專案(captions.json + index.html)
    專案筆記.md        這支的錯字表/選曲/文案/進度(隔天回來先讀,範本在 tools/freecut/templates/)
```

**審片區 = 給使用者的窗口。** 每次要請使用者審,就把「當前 preview + 字幕」複製進去並重產 `開始審片.html`(見第 4 步),裡面永遠只有這三個檔 — `make_review_page.py` 產完會**直接用瀏覽器幫他打開**,他不用找資料夾、不用拖檔案。舊版本直接覆蓋,不留歷史。

**★ 要使用者開任何檔案或資料夾,一律你幫他開,不要只給路徑。** 用 `"$PY" "$H/open_file.py" <檔案>`(打開)或加 `--reveal`(在 Finder／檔案總管裡把它選起來)。學員回報 15 次「審片區在哪」「我找不到資料夾」「成品在哪」(Windows 8、Mac 7;Windows 的工具包裝在 `C:\Users\<帳號>\` 深處),AI 直接幫他開的那幾次全部一次解決。也**不要給 markdown 相對連結**:那是相對於你的工作區、不是工具包,學員點了找不到(實測,她列為最不爽的一點)。開不了(沙盒擋住)時 open_file 會印出完整路徑 — 先用沙盒外權限重跑,還是不行才把**完整路徑**貼給他請他雙擊。

**配方 vs 媒體**:`transcripts/`、`edl.json`、`captions/*.json`、`專案筆記.md` 是「配方」(文字、極小、隔天要用,cleanup 保留);preview、render、擷取圖、node_modules、審片區的影片是「媒體」(大、可重生,cleanup 刪)。**例外:專案完成後,審片區裡的最終版(影片 + 字幕.json)保留不刪** — 那是使用者重看成品的窗口(cleanup.sh 已內建這個例外)。

紀律(照做,他的硬碟才不會爆):
- 每個中間檔都放 `工作檔/` 底下。絕不把 preview、render、擷取的 PNG、試聽的音檔散在最上層或旁邊的資料夾。
- 舊的 preview 邊做邊刪 — 有了 `preview_v2` 就刪掉 `preview_v1`。只留最新的 preview + `edl.json`。
- 擷取的畫面 PNG、試聽下載的音檔是用完即丟:看完馬上刪。
- **一次工作結束時,主動問要不要清理:**「要不要幫你清一下工作檔?我會刪掉大媒體檔(preview、擷取的圖、node_modules),但**留下配方文字檔**(edl.json、逐字稿、captions、專案筆記),下次回來重跑 render 就好,不用重轉稿重對時間。」顯示大小,等他說好。
- 使用者說「清理」「太亂了」時,跑 `bash tools/cleanup.sh <專案資料夾>`(安全 — 先顯示要刪什麼並要你確認;**只刪大媒體檔 + 可重生資料夾,保留所有文字配方**)。**絕不刪原始影片或成品.mp4。** 重點:配方檔(edl.json、transcripts/、captions/*.json/*.html、專案筆記.md)加起來通常 <1MB,卻是隔天回來的省時關鍵 — 別跟著媒體一起刪。

## 素材庫與 b-roll — 建議循環

`KIT/素材庫/` 是跨專案共用的可重複素材:`背景音樂/`、`音效/`、`b-roll/`、`圖片/`。詳見 `KIT/素材庫/說明.md`。

- 剪片要用音樂／音效／圖片／b-roll 時,**先看素材庫有沒有現成的**,有就直接用,不要重新下載。
- 使用者這次帶進來或下載了新的音樂／音效／圖片/b-roll,用完後**主動問**:「要不要把這個存進素材庫,下次可以重複用?」說要就幫他放進對的子資料夾。
- **b-roll**(補充畫面)放 `素材庫/b-roll/`:空景、產品特寫、示範操作畫面,任何口播中間想切過去的畫面。剪片時遇到適合插 b-roll 的段落(例如講到某個具體東西),**主動提醒**:「這裡可以插一段畫面,你素材庫裡有沒有相關的?或想拍一段?」這是**建議**,放哪、放不放由使用者決定,不要自動塞。實際怎麼合成見流程「5.5 插 b-roll(選配)」。
- **他自己拍的畫面永遠優先,但動畫是預設配備,不是備胎。** 每支預設提 2-3 段「動態 b-roll」(用動畫把那句話演出來),挑腳本裡講步驟、數字、對話、情境的句子;他有真實畫面的那句就用真實畫面。見 `tools/特效工具箱.md` 第 6、7 點。(2026-09-30 Jake:「預設就多一些動畫,不要我說了再增加」— 選段demo 第一版提案只放一段動畫,他開口問了才補兩段。)

## 硬性工作順序 — 先鎖定「剪對了」再花錢

這是流程唯一的硬規則。它只管「順序」跟「檢查」,不管風格、節奏、特效(那些永遠是活的、量身的)。之所以要硬,是因為實測踩過:字幕/剪接的錯留到合成之後才發現,每修一次就是一次 3 分鐘 render + 重混音;而同樣的錯在「還是文字」的階段修,是 5 秒的事。原則:**上游沒鎖,絕不動下游。**

```
A. 轉逐字稿 → 一次把所有 xref 旗標用 split_blobs 查完(不要邊被嫌邊查)
B. 結構剪接 → 寫 edl.json → render preview(--preview,無字幕)
C. 機器對稿:verify_cut.py 比對 preview 跟「應該講的話」,先幫你抓出接縫 bug
      (夾字、漏字、兩句相撞)——這關過了,使用者才會看到版本
D. 出字幕(先當文字,還沒燒進畫面):gen_captions 產 captions.json
E. 使用者用「preview + 字幕檔」在 審片.html 看:一次收「剪接 + 字幕」的回饋
      (剪接類/字幕錯字/斷句,全部這輪一起改,都還很便宜)
F. 鎖定 → 剪接跟字幕文字從此不再動
      ★ 這是硬關卡,不是你自己心裡默認的。要**明講、等他回一個「好」**才算鎖:
        「剪接跟字幕我看是對了 — 這版的『講什麼、怎麼斷句』就定了喔?我按下去就開始加特效跟配樂,
         之後那些要再改剪接會比較費工。可以往下嗎?」他沒明確說可以,就不要碰 G。
G. 才開始:節奏提案 → 特效/運鏡/b-roll/吉祥物角色 → 合成 render
H. 音效 + 背景音樂混音 → 成品.mp4
```

**文字是地圖,不是裁判。** 使用者永遠用「有畫面的版本」下判斷(眼睛看死白/搖頭空白/醜接點、耳朵聽節奏),文字只是拿來精準指位置。所以 C 之後一定給 preview,不是只給一段文字要他核准。preview 很便宜(1 分鐘內),沒有理由拖到最後才給畫面。

**★ 要他確認的短片段,直接放進對話裡給他看,不要叫他去資料夾找。**
接縫預覽、原檔小樣、2-3 個選一的比較樣本 —— 這些都是幾秒鐘的小檔,直接送進對話,
他點開就聽,幾秒鐘就回你。叫他「打開 工作檔/ 找 接縫預覽.mp4」則是要他切換視窗、
找資料夾、開播放器,而且他很可能開錯檔案或懶得開。實測回饋:直接放對話「很快又直覺」。
分界很簡單:**整支要審 → 審片區的 開始審片.html(他要能標註解);單點要確認 → 直接丟對話。**
(給多個選項時檔名要帶參數,例如 `結尾B_尾段從49.05.mp4`,他才知道在挑什麼。)

**用字幕句指位置,不要用秒數。** 秒數每重剪一次就位移,講「那句『那中英的』不對」比講「1:04」穩,而且 審片.html 可以直接點那句跳過去。

## 剪輯流程

在 `<專案>/工作檔/` 裡作業(就是下面的 `--edit-dir`)。最後成品輸出到 `<專案>/成品.mp4`。照上面的「硬性工作順序」跑。

### 1. 轉逐字稿 + 交叉比對(剪之前先做)

**使用者給的是「長錄影選段」清單的某一支?先用它起第一版剪點,不要從頭找。** 選段清單(student-cutlist / reel-cutlist 產的 PDF,旁邊有同名 .html)每一支都寫好了原片時間碼、跳剪順序、字幕逐句、開頭字卡 —— 那是已經做過的判斷,從頭轉整支長錄影再找一次是浪費(選段demo 2026-09-29 復盤)。
```bash
$PY $H/cutlist_to_edl.py <選段.html 或 .pdf> <第幾支> <長錄影> KIT/我的影片/<專案名>
```
它會:切出涵蓋這幾段 ± 3 秒的片段當這支的原始影片(自動轉正、4K 縮到 1080)、把清單的「秒」級時間碼對到附近真的停頓、連續的兩列自動併成一段,寫出 `工作檔/edl.json` 跟 `工作檔/選段資訊.md`(開頭字卡、字幕逐句、定格點、不可掃到 —— 當腳本參考)。**這是提案底稿**:接著照下面照常轉「那個片段」的逐字稿、xref 旗標全部查完、句內停頓收短、render、verify_cut。標「附近沒有明顯停頓」的剪點一定要拉波形。清單上的字幕逐句跟影片對不上,一律以影片為準。

**開場先問一句:有沒有腳本?** 「有腳本嗎?有的話直接貼進對話框給我最方便(腳本是小文字檔,不像影片要丟資料夾),或丟進資料夾也行,當參考、字幕會對得更準。」有就讀,沒有照樣剪。**腳本是參考,不是真相** — 使用者即興改詞、跳過、加詞很正常,腳本跟影片對不上的地方**一律以影片(耳朵聽到的)為準**,絕不硬把字幕改成腳本。怎麼用:
- **對錯字**:Whisper 某個詞含糊/怪,腳本剛好有對得上的詞,**而且音訊聽起來就是那個** → 才加進 `fixes.json`。保守加,只補高把握的,不要整段拿腳本覆蓋字幕。
- **補 GAP**:GAP 旗標(吞掉的半句)時,腳本給「大概講了什麼」的線索,但**還是要對波形/音訊確認**再補,不要憑腳本硬塞。
- **剪接參考**:知道完整內容,誤剪比較容易發現、救得回;但剪什麼還是照實際講的。

```bash
$PY $H/transcribe.py <影片> --backend whisper --language zh --edit-dir <專案>/工作檔
$PY $H/xref_silence.py <影片> <專案>/工作檔/transcripts/<名稱>.json
```

- **讀逐字稿讀 `transcripts/<名稱>.words.txt`(compact 版),不要讀那份肥 JSON。** transcribe 會順手產這份一行一字的檔(`idx  start-end  字`),token 只有 JSON 的約 1/6。剪接、對時間、規劃字幕要的都在這份。
- **一次把 xref 的所有旗標查完,不要邊被使用者嫌邊查。** 五類旗標 MERGE / LONG / **GAP** / **FILLER** / **SNAP** 每個都跑 `$PY $H/split_blobs.py <影片> <start> <end>`,在提剪接案之前就把真正的語音區塊看清楚。MERGE 區是 Whisper 出錯的地方(重複字被併成一個 token、贅字被吃進字的時間裡);實測**幾乎每個接縫 bug 都落在這些旗標區**。絕不在旗標區只憑逐字稿時間做細剪。這關先做完,後面才不會來回。
- **FILLER 旗標 = 這個「字」可能根本不是字,是 um/呃。** Whisper 會把一個 0.28 秒的
  氣音轉成一個正常的字(實測:開頭那個 um 變成「你」,而使用者從頭到尾沒講過「你」)。
  逐字稿裡它看起來完全正常,下游沒有任何東西看得出來。**剪之前先確認,絕對不要把鉤子
  或第一句建在 FILLER 上面** — 實測害使用者多審一輪才發現「開頭有個 um」。
- **SNAP 旗標 = 短促爆音(彈指/拍手/敲桌),逐字稿沒有它,預設靜音門檻也看不到。**
  **不要把它當成靜音修掉** — 使用者會發現「我的彈指不見了」(實測發生過)。
  要對特效/音效就用 SNAP 報的秒數。
- **GAP 旗標 = 有聲音但逐字稿沒有字,一定要查到底。** 這是 Whisper 最陰的盲區:講一半的字、口誤起頭、小聲重複,被整個吃掉,逐字稿裡**完全不存在**,所以下游沒有任何工具看得到它 — 只有 xref 拿逐字稿去對真實音訊才抓得出來。對每個 GAP 跑 split_blobs + 波形看那段到底是什麼聲音;**看波形/影格還是判斷不出來講了什麼,直接問使用者**:「X.X–X.X 這裡有一段聲音但機器沒聽出字,你聽一下是講了什麼?」— 絕不繞著它瞎剪。實測「結尾一直剪錯字」整整來回十輪,兇手就是一個被吞掉、GAP 才抓得到的半句「怎麼」。
- **沿用舊剪點時,旗標審查不繼承「已驗證」。** 重剪或續剪、拿上一版(甚至已出過成品)的 edl.json 當底稿時,那份剪點只是**提案底稿**,不是通過驗證的保證 — 舊成品很可能本來就帶著沒被抓到的瑕疵(GAP 盲區尤其會這樣潛伏)。三類旗標照樣從頭全部重查一遍,不要因為「上次鎖過了」就跳過。
- **逐字稿的誤聽不會自己舉手 — 使用者說他講了 X,就信他。** Whisper 同音/人名誤聽率高(學員實測:「案子接不完」→「暗直接不玩」、「帆布袋」→「反正不戴」、人名 Zoe →「肉依」),而且整句錯得離譜時,AI 反而容易拿逐字稿去「糾正」使用者、或把其實是鉤子的句子當廢話剪掉。鐵則:
  1. 使用者說某段有講某個詞,**以他為準**,回逐字稿找**音近字**對位置,絕不拿逐字稿反駁他(「帆布袋」事件就是 AI 回「你沒講這個」,實際上逐字稿寫成「反正不戴」)。
  2. 開頭/結尾出現不知所云的整句,先把那段**原音切出來丟對話**問「這段在講什麼」,不要憑字面判斷它是廢話。
  3. 人名/品牌/專有名詞開場就問寫法,直接進 fixes.json。
- **不要讀 `hyperframes init` 產生的 `transcript.json`。** 它會用自己的英文小模型把中文影片重轉一份,整份是幻覺(實測整段「I think it is important…」重複幾十遍,燒掉幾萬 token)。字幕一律以 `工作檔/transcripts/` 這份為準。

### 2. 結構剪接(第一輪 — 依逐字稿)

**預設直接剪出 v1,不要先問。** 使用者丟進來就直接判斷哪個 take 留、哪些 NG／重拍刪、哪些停頓修短,寫 `工作檔/edl.json` → render `preview_v1`,然後把「剪掉了什麼」清單跟 preview 一起給他審。**不要先丟一段文字提案要他核准** — 他要用「看得到的版本」判斷,不是憑文字想像(C 之後一定給 preview,preview 很便宜)。**句間留白不要整支固定同一個值** — 短影音從約 250ms 起跳,要衝節奏就收到 150ms,關鍵句／轉折前放到 400ms 以上讓它喘一口。太緊(130ms 以下)會很躁,太鬆(400ms+ 全程)會拖。

**唯一先問的例外:素材真的很雜** — 同一句講很多次分不出留哪個 take、完全沒腳本又東講西講抓不到主線。這種才在剪之前先問**一句白話的**:「我打算留 X、砍 Y,這樣嗎?」問完就剪。**絕不用「敘事線」這種詞** — 講人話,講你要留什麼、砍什麼。有腳本時連這一步通常都不用(見第 1 步開頭「有沒有腳本」那段),照著剪就好。

edl.json 格式:

```json
{"version":1,"sources":{"NAME":"/abs/path.MOV"},
 "ranges":[{"source":"NAME","start":1.53,"end":7.54,"beat":"HOOK","quote":"...","reason":"..."}],
 "grade":"none","overlays":[],"subtitles":null,"total_duration_s":0}
```

range 的時間全部用**原始影片的秒數**。輸出:`$PY $H/render.py 工作檔/edl.json -o 工作檔/preview_v1.mp4 --preview --no-subtitles`

**「剪掉了什麼」清單(每一版都要維護)。** 剪完 v1 時跟每次重剪後,列一份編號清單:每段被剪掉的範圍 + **它裡面講了什麼**(從逐字稿抄,前幾個字即可)+ 為什麼剪。例:「3. (0:42–0:47) 剪掉:『那個我們家的貓昨天…』— 離題」。寫進 `工作檔/專案筆記.md`(每版覆蓋更新)。這是使用者唯一能「看到不見的東西」的窗口 — 沒有它,剪太多時他只能回去重看整支原片(實測回報的痛點)。開剪前先講一句定心丸:「剪掉的都還在原始檔裡,任何一段隨時救得回來 — 想比對就跟我說,我列給你看。」使用者說「剪太多了」「原本那句呢」時,**第一動作是把這份清單拿出來**問他要救回哪段(EDL 記的是原始影片秒數,救回 = 把那段 range 加回 edl.json 重 render,無損),絕不要請他回去重看原片找。

### 3. 細剪(第二輪 — 使用者主導,用波形當真相)

使用者用耳朵聽 preview。任何要修的地方:
- 跑 `$PY $H/timeline_view.py <原始影片> <start> <end> --n-frames 20 -o wave.png` 給他看 — 使用者從波形的時間軸讀出精確秒數。
- 修正一律用**原始影片時間**(重剪也不會跑掉)。輸出時間軸的秒數每次重剪都會位移 — 絕不拿舊數字去加減offset。
- 你聽不到聲音。字到底是什麼字,由使用者的耳朵或波形決定,不要重跑 Whisper(換大模型不會解決重複字問題)。
- **剪點留白有預設值,不要貼著語音零緩衝下刀。** 一段話結束後,收尾點放在字尾語音**之後 0.08–0.12 秒**(留一點自然衰減,不然聽起來像被硬切掉);下一段的起點放在下一個字語音**之前約 0.05 秒**(catch 到起音、又不帶進前面的贅字尾);句與句之間收尾至少留 0.15 秒。實測好幾輪「太緊/太鬆」就是因為剪點貼在 split_blobs 的 blob 邊緣、零緩衝。這些是**起始預設**,使用者說更緊/更鬆再照他的耳朵調。
- **什麼時候要拉波形(不是每刀都拉,太貴)。** 三種情況必拉 `timeline_view` + `split_blobs` 把落點放準:①xref 的旗標區(MERGE/LONG/GAP);②使用者回報接不順/有殘留的那個縫;③GAP 這種「有聲音卻沒有字」的地方。剪點落在明顯乾淨靜音裡的,憑 words.txt 時間下刀即可,不必每刀都拉圖。

**每次 render 完 preview,先自己做兩件事,再拿給使用者:**

1. **機器對稿(接縫檢查)** — 這關幫你把接縫 bug 擋在使用者看到之前:
   ```bash
   $PY $H/verify_cut.py <專案>/工作檔/preview_vN.mp4 \
       <專案>/工作檔/transcripts/<名稱>.json <專案>/工作檔/edl.json --fixes fixes.json
   ```
   它重聽 preview、跟「EDL 該講的話」比對,只回報**結構性**的差異(某字被夾掉、某段漏進來、兩句相撞),Whisper 的小誤聽會自動抵消。有旗標的點,用波形/擷取影格確認再修。這關過了(或旗標都確認過)才給使用者看。
   > **verify_cut 對「重複字/半截字」天生是瞎的。** 它重聽 preview 也是用 Whisper,而 Whisper 會**再次**把重複、講一半的字去重/吃掉,所以那段瑕疵在對稿裡一樣不存在 → 對稿照樣「通過」。**「verify_cut 過了」不等於「沒有重複、沒有殘留半句」。** 使用者的耳朵在這件事上永遠贏過對稿:他說某處有重複/多了半句,以他 + split_blobs 波形對帳為準,**絕不能拿「對稿通過/逐字稿是乾淨的」回他**。
2. **整句讀回** — 別只在心裡想接縫。把剪出來的句子當**連續腳本**讀一遍(可直接看 verify_cut 的比對,或重轉 preview 讀 words.txt),確認沒有半句話、沒有殘留的重複、沒有主詞相撞(例:剪掉中間後「我自己」直接撞「我大概」會不通順)。這個檢查花 10 秒、零張圖,是必做,不是等使用者來抓。

**不要幫沒聽清楚的字瞎猜。** 錯字修正只改「明確聽得出來」的字;拿不準的字(尤其 MERGE 區、中英夾雜)一次列給使用者確認,不要自己編一個(實測「總而言之」被瞎猜成「那中英的」,連錯字字典都跟著錯)。

### 3.5 節奏提案(這步是靈魂)

> 順序上這是「硬性工作順序」的 **G**:等剪接跟字幕文字都在 審片 那輪鎖定之後才做,不是剪完馬上做。放在這裡是因為它接著第 5/5.5 步的特效執行。鎖定前不要開始堆特效。

新手不會自己判斷哪裡該加什麼。**由你(AI)讀逐字稿,對這支影片提一份具體的節奏提案**,預設值先幫他填好,讓他說「好」就有 80 分,想改再改。工具箱是你的調色盤,不是丟給他自己選。

鉤子先講(前 3 秒決定有沒有人看下去,最需要引導):

**A. 鉤子 = 口語鉤子 + 視覺鉤子**
- **口語鉤子**:他錄的第一句 → 剪緊、不留死白、快速落地(放大他錄的,不是幫他選鉤子)。
- **視覺鉤子**(重點,多花力氣引導):讀懂第一句在講什麼,主動說「你的鉤子在講 X,前 3 秒放一個 X 的畫面」。
  - 有相關圖片／b-roll → 用他的。沒有 → 從 `tools/特效工具箱.md` 挑一個適合「這一句」的:開場字卡轟炸、動態 b-roll、文字／圖文卡(`tools/overlay-cards.md`)… 依第一句的內容跟語氣判斷,不要每支都同一招(不用素材,新手也一定有視覺鉤子)。
  - 課程核心原則:第一句一定要「把講的東西用畫面呈現出來」,加了視覺就放大。

**B. 其餘節奏工具(預設力度抓 75 分,有用量上限)**

預設提案的力度目標是 **75 分**,不是保守的 60、也不是全上 100。為什麼:100 分 = 每個 beat 都設計(像 demo 片),會多好幾輪 render 跟幾萬 token;75 分 = 挑最有力的點做滿,有記憶點、成本合理。使用者說「做滿一點」再加,說「簡單就好」再減。以 60-90 秒口播為基準,預設量:
- 字幕塗黃 3-4 個 · 運鏡(punch-in / step-zoom 合計)2-3 處 · 圖文卡 1-2 張
- **動態 b-roll(動畫)2-3 段是預設**,不是「沒素材才補」:講步驟/流程 → 清單或流程面板;講數字/比例 → 讓數字「發生」(例:10 個小人 9 個變紅);講他跟客人的對話 → 對話框逐字打出原話;講情緒 → 情緒堆疊。真實畫面另計(他拍的、或原片裡剛好拍到的那個東西),有就優先用 · SFX 2-5 個點 + BGM 全程 · 彩蛋類(縮框吐槽/吉祥物)0-1 個
- 「大」工具(開場字卡轟炸、重點重擊、頭後大字、動態 b-roll、真實畫面切換)合計通常 3-5 個,放在最有力的那幾句。提案時動畫已經在清單裡,不要等使用者問「有沒有動畫」

這些數字是力度的參考,不是配額。

配音效跟運鏡時,**照 `素材庫/預設包/對照表.md` 的「情緒/字眼 → 音效+運鏡」準則配**(riser 鋪在揭曉前、pop 配列點、punch-in 配強調句…素材就在預設包裡)。把它當工具箱:挑對的、在對的點、不疊在同一拍。各工具的用法:
- **字幕關鍵字 highlight**:整支挑 3-4 個最有力的詞塗黃,不是每句;已經有 b-roll／推鏡的那個點就不要再疊。**使用者在審片時反白/【詞】自己標過的優先算進額度**,你只補提案剩下的名額(他標太多就提醒超過上限,一起挑掉)。
- **切走 cutaway**:講到現場沒拍到／需要看到的具體東西 → 短暫全屏切過去,人聲不斷。要他的素材,沒有就跳過(不卡)。
- **畫中畫 PiP**:靈活用(表情／反應重要時保留臉,或任何時候覺得有用)。
- **疊加卡片(下標／數字卡／圖文卡)**:名字頭銜「下標」、成果數字「數字卡」、抽象東西的圖文卡 → 做法 + 5 款驗過的樣式(乾淨橫條/膠囊/毛玻璃/實心/毛玻璃數字卡)見 `tools/overlay-cards.md`。下標=講你是誰、數字卡=強調重點,底層同一塊積木。一張 ~1-3 秒,節制用、待在安全區。
- **運鏡動態**(讓畫面活起來,已驗證,做法見 5.1):
  - **推鏡 punch-in／拉遠 punch-out**:同一段口播畫面放大／縮小,像換第二機位或強調某句。
  - **平移 pan**:畫面左右緩緩移。
  - **靜態圖 Ken Burns**:插進來的靜態圖片加緩慢縮放+平移,不要死板一張。
  - **縮框(吐槽用)**:講到梗／反差時,整個畫面**瞬間**縮小露出黑邊 — 瞬切不是平滑動畫,突然才好笑。
- **特效工具箱**(`tools/特效工具箱.md`,驗證過的做法都在裡面):
  - **開場字卡轟炸** — 話變成一張張大字卡在頭上方硬切,關鍵那張紅字砸進來。很衝。
  - **重點重擊** — 最重的那幾個字超大亮黃、一個字一個字砸下來。只用在那幾個字。
  - **頭後大字** — 關鍵詞超大、放在頭的後面(要多跑一步去背)。電影感。
  - **字幕強調** — 手繪圈、手繪底線、整框翻色(跟塗黃同一個額度)。
  - **畫面讓位** — 人縮成卡片、縮到角落小窗,或整個蓋掉,讓位給動態 b-roll。
  - **動態 b-roll** — 沒素材時,用動畫把那句話演出來(情緒堆疊、流程說明面板…),內容一定是他講的事、他的行業。
  - 這些是**調色盤,不是對照表**:沒有「鉤子一律用字卡」「數字一律用重擊」這種規則。每一個都是你讀完這支腳本後,判斷「這一句」適不適合。使用者想先看長什麼樣 → 請他雙擊 `tools/特效型錄/index.html`(參考用,提案還是你出)。

**提案格式**:列一份簡短、可勾選的清單(時間點 + 做什麼 + **一句為什麼是這支的這裡**),預設值先幫他填好。用到要去背的工具,順便講一句「這個要多跑一步」(舊電腦 Intel / 8GB 就別提去背)。特效工具的提案跟其他提案**同一張清單一次問完**,不要另開一輪;位置、字級、配色這種技術判斷不用問。使用者說「好」就照做;要改就改某一條。需要他素材的(cutaway／圖片)問一句「有沒有?沒有就跳過」——**絕不因為缺素材卡住**,其餘照樣到 80 分。這份提案接著就是第 4/5/5.5 步的執行清單。

**防套版**:提案是針對「這支的腳本、他的鉤子詞、他強調的地方」量身出的,不是固定模板;加上用量上限,天生就克制。不要出現機械式 pattern(不要「永遠第 3 個字塗黃」「永遠 2 秒切」)。**跨影片也要有變化**:提案前看 `專案筆記.md`／`我的剪輯偏好.md` 記的「上一支用了哪些工具」,不要支支同一套;這支用了什麼,做完記進專案筆記。

### 4. 字幕(硬性順序的 D — 先當文字,還沒特效)

字幕在**剪接鎖定前**就要出,而且**先當文字檔給使用者核**(斷句、錯字、highlight 都是文字階段的 5 秒修改)。順序:先產 captions.json → gen_captions 產乾淨的 index.html → 使用者在 審片.html 看 preview + 這份字幕。

**第一步:captions.json(時間 + 斷句 + highlight)**
```bash
$PY $H/edl_to_captions.py <transcript.json> <edl.json> -o captions.json --fixes fixes.json
```
它做 EDL 重算、英文碎片合併、時間夾緊、斷句分組。跑完你只做判斷層:修錯字(只改聽得清楚的)、調斷句、挑 highlight。

- **斷行只落在詞與詞之間**(jieba 斷詞,setup 會裝):Whisper 常把中文切成單字 token,舊版會斷出「自/然」「收進/去了」(三支舊專案實測 2/19/14 處 → 0)。也不會斷在「很｜自然」「講｜的時候」這種位置。
- **停頓從聲音量,不從逐字稿算**:Whisper 中文字級時間是黏著的,停頓被算進前一個字,`w.s - prev.e` 幾乎都是 0。EDL 模式自動用 EDL 的來源影片量;門檻依每支錄音的底噪/人聲自動算。
- **句頭被吃掉時(Whisper 時間系統性偏早)**:改成重轉剪好的 preview,再用它自己的逐字稿出字幕:
  `$PY $H/edl_to_captions.py <preview 的逐字稿.json> --no-edl --audio 工作檔/preview_vN.mp4 -o captions.json --fixes fixes.json`
- 斷句還是要你讀一遍調:工具保證「不切詞」,不保證「每行都是最自然的一句話」。**上字幕前把斷句清單當文字給使用者看**,讓他重斷。改斷句 / highlight 就在 captions.json 裡加 `"hl":"某詞"`(整句期間塗黃,靜態)。每次剪接改動後從頭重跑,絕不拿舊數字加減。

**第二步:gen_captions 產 index.html(不要手寫)**
```bash
mkdir -p <專案>/工作檔/captions && cd 進去
npx hyperframes init . --non-interactive --video ../preview_vN.mp4   # 只為了拿 npm 專案骨架
$PY $H/gen_captions.py ../captions.json --video ../preview_vN.mp4 \
    --w 1080 --h 1920 --duration <ffprobe量到的秒數> --font 宋體 -o index.html
```
`gen_captions` 把「工程上會出錯的部分」全部封好了(這些坑手寫必踩):影片 `data-start="0"`、字幕 `z-index` 要壓過影片不然字幕跑到影片後面看不到、每個 clip 要 `class="clip"`+`data-*`+唯一 id、`@font-face` 不寫字型會 fallback 成黑體。它留了 `CREATIVE LAYER` / `CREATIVE TIMELINE` 兩個插槽給你加特效(第 5/5.5 步)。**框架穩、內容活** — 斷句/highlight/特效都還是你量身出的。

**★ 加過特效之後不要再重跑 `gen_captions`** — 它是整份重產 index.html,你寫在 CREATIVE LAYER /
CREATIVE TIMELINE 的東西會全部不見。特效層鋪下去以後,字幕的字級、位置、內容改動請直接改 index.html。
**字級跟位置一律用參數,不要手改 CSS**(手改的下次重產就沒了):`--font-size 66`(預設 56)、
`--sub-bottom 340px`(預設 `var(--safe-bottom)` = 451px)。**低於 450px 會進到 IG 介面區**
(帳號列、進度條會蓋到),使用者說「字幕再低一點」就照做,但要跟他講這個取捨。

**長句自動縮字級**:字幕是不換行、置中,超過字幕框(左右讓出按鈕欄,1080 寬時約 790px 可用)會往右溢出被切掉。`gen_captions` 會逐句量寬度,只把放不下的那幾句縮到剛好,並印出是哪幾句 —— 不用自己在特效層補(選段demo 2026-09-29:字級 66 時 13 字以上的句子全部溢出,成品審片才被抓到)。

字型:**兩個預設用中文名讓使用者選**(第一次問,記進偏好檔):**宋體**(襯線、文青,`--font 宋體`)/ **黑體**(無襯線、有力、短影音常見,`--font 黑體`)。**highlight 只換顏色(黃),絕不換字型。**

字幕樣式:`--style` 共 6 款,預設 `classic`(現行黑框,不指定就用它)。變化款:`clean`(乾淨無框粗體)/ `outline`(描邊 TikTok 風)/ `neon`(霓虹發光)/ `gradient`(漸層填色)/ `emphasis`(關鍵字放大)。全純 CSS、直式原生、免下載。第一次可問使用者偏好、記進偏好檔;`emphasis` 款是把 highlight 的關鍵字**放大**(其餘款塗黃)。

安全區:gen_captions 已自動把字幕放進 **IG Reels 安全區**(上 ~220 / 下 ~450 / 左 ~50 / 右 ~100 px,`--safe-*` CSS 變數可調),字幕不會被 IG 介面蓋到。你在 CREATIVE LAYER 加字卡 / callout / logo / lower-third 時,一律用 `var(--safe-*)` 待在區內,重要元素別進下 450px 與右 100px。

色調:預設是**自動微調(乾淨、不套風格)**。另有學員可挑的色調款(`grade.py` preset):`warm` 暖色/親和、`cool` 冷色/專業、`clean` 明亮乾淨(短影音常見)、`muted` 低飽和高級感、`cinematic` 電影感。學員想要某種調性再套(`python $H/grade.py --list-presets` 印每款白話說明)。第一次可問偏好、記進偏好檔。

其他鐵則:句子層級字幕、連續講話不留空檔;**不做逐字卡拉OK highlight**(Whisper 逐字時間不夠準,量產會出包);`data-duration` 用 ffprobe 實際量到的長度不用 EDL 加總(loudnorm 會多約 0.2 秒)。

改完一定 `npx hyperframes lint` → 修掉 error → render。

**第三步:整備審片區,使用者在 審片.html 核(硬性順序的 E)**

先把「要審的兩個檔」放進專案的 `審片區/`(使用者唯一要開的資料夾,舊的直接覆蓋):
```bash
mkdir -p "<專案>/審片區"
# ★ 影片會被 make_review_page 自動放進審片區「同一層」(macOS 是 APFS clone,
#   秒複製、不佔額外空間)。以前那條「用 ../ 相對路徑指過去就好」的規則已撤銷:
#   那個實測只在部分 Chrome 環境成立,Safari 擋 file:// 往上層抓檔,只有 Safari 的
#   原廠 Mac(很常見)頁面會一片空白 — 學員完全無法審片還以為自己弄壞了(實測回報)。
cp "<專案>/工作檔/captions/captions.json" "<專案>/審片區/字幕.json"
# 樣式側檔一起帶(gen_captions 產的)— 審片頁的預覽字幕才會跟成品同字型/字級/位置,
# 使用者不會對「不存在的問題」下指令(字級誤報跑出鏡、字型不對白繞,實測回報)
cp "<專案>/工作檔/captions/樣式.json" "<專案>/審片區/樣式.json" 2>/dev/null || true
# 產「開始審片.html」— 影片+字幕都內嵌好,使用者雙擊就開審,零拖檔
"$PY" "$H/make_review_page.py" "<專案>/審片區" "../工作檔/preview_vN.mp4"
# 收尾時換成成品:"$PY" "$H/make_review_page.py" "<專案>/審片區" "../成品.mp4"
# 放的是「字幕已經燒進畫面」的成品時,加 --burned-in(檔名以「成品」開頭會自動判斷),
# 否則審片頁會在燒好的字幕上面再疊一層預覽字幕 → 畫面上兩層字幕重疊。
```
`make_review_page.py` 最後會自動把 開始審片.html 用瀏覽器打開(輸出 `[已幫使用者打開]`;不想開時加 `--no-open`)。然後告訴使用者:
> 審片頁已經幫你用瀏覽器打開了,影片跟字幕都載好,直接開始審。(沒看到的話跟我說,我再幫你開一次。)

輸出是 `[沒能自動打開]` 時:用沙盒外權限重跑一次 `"$PY" "$H/open_file.py" "<專案>/審片區/開始審片.html"`;還是不行,才把它印出的**完整路徑**貼給使用者請他雙擊。(最後備用:開工具包根目錄的 `審片.html`,把審片區的影片 + 字幕.json 拖進去。)**字幕是審片頁疊上去的,直接點開 mp4 看不到字幕是正常的,不是字幕不見了。**

(最後那句一定要講:preview mp4 本身沒燒字幕,學員直接點影片看,以為字幕消失了 — 實測回報。)

**跟使用者說「審片區更新好了」之前,比對一次 `審片區/<影片>` 跟來源的大小**(`ls -l` 兩個都看)。舊版 make_review_page 碰到同名影片不會覆蓋,學員連續兩支片審到舊版(已修,但這個確認很便宜)。

他看得到字幕句、點句子跳位、雙擊改錯字/打「/」斷句/併下句/用【詞】標塗黃(影片上即時看到黃字效果)、拖區間剪掉幾秒到幾秒 — 全部動作都會變成註解,最後一次「複製全部」貼回來。這輪一次收「剪接 + 字幕錯字 + 斷句」全部的回饋,一起改,都還便宜。收斂後才鎖定,進第 5 步特效。**每出新版 preview,重跑上面的 cp + make_review_page.py 覆蓋審片區**(開始審片.html 內嵌的是產生當下的字幕,不重產就是舊的)。

**貼回來的註解裡有「附畫記圖 審片-X-XX.png」時:直接去使用者的「下載」資料夾讀那些圖**(Mac `~/Downloads/`、Windows `%USERPROFILE%\Downloads\`,檔名就是註解裡寫的)。審片工具在他按「複製全部」時已自動把圖存進去了 — **絕不請使用者上傳或拖圖給你**。紅筆圈的就是位置。

### 5. 特效(選配)

> ★ **進這步之前先確認硬關卡 F 過了** — 使用者有沒有明確對「剪接 + 字幕」點頭?沒有就回上一步收乾淨、拿到那個「好」再來。**特效/配樂是最貴的一層,一旦鋪下去,回頭改剪接就要整支重 render。** 實測炸過:剪接還沒對就把整支特效配樂全做完,結果一個 0.9 秒的剪點修兩次、每次重 render 整支 15 分鐘,還把有瑕疵的成品發出去了。剪對 > 剪炫。不要把兩層混在同一輪做。

GSAP 疊層,跟字幕同一個 composition。**提案裡用到特效工具箱的工具,照 `tools/特效工具箱.md` 的做法寫**(每個工具的程式碼 + 踩過的坑都在那;動態 b-roll 的完整範例在 `tools/特效型錄/範例-動態b-roll.html`)。那份的「共通規則」一定要照:
- **大特效掛在「審片鎖定的字幕句首」**,不要逐字對時 —— 字級時間不準,實測用音量切、用短片重跑 Whisper 都失敗過。重擊類只用在短的那幾個字,整句一個字一個字砸會蓋臉又對不上。
- 中文大字要指定粗黑中文字體(英文字體沒有中文,會退成細字);字級用字數算;超過 12 字的字幕要縮字級(不然會偏一邊被切掉)。
- 加完先 `npx hyperframes snapshot --at 秒數,秒數 --no-end` 看位置、出界、蓋臉,再 render。
- **設計類畫面(動態 b-roll、自己畫的圖、大字、字卡)先把 snapshot 拼成一張圖給使用者看,他說好才 render** —— 學員原話「在你輸出影片檔前,先把生成好的圖片傳給我看」。他給了參考圖就照著描(半透明疊上去對齊),不要憑印象重畫;改的時候只改他點名的那一項。
- 句首 ≠ 開口:字幕句常從換氣空白開始,大特效落下前量一下那句開頭的音量,晚開口就往後挪。

- 對手勢／動作的特效,「放哪」「什麼時候」是**視覺問題**:擷取影格(`ffmpeg -ss T -i vid -vframes 1 f.png`)去看,把元素放在手／動作的位置。逐字稿沒辦法告訴你手在哪、手指什麼時候彈。
- 用真的品牌素材,不要自己畫(catalog 沒有的使用者自己給 — 資料庫有缺是正常的)
- 只用有限次重複、cubic easing,重疊的 tween 加 `overwrite:"auto"`

### 5.1 運鏡動態(推鏡／平移／Ken Burns／縮框)— 做法與驗證過的坑

動態全部是**用 GSAP 動 `transform`(scale / x / y)**在同一個 composition,不重壓影片。共通做法 + 踩過的坑:

- **推鏡 / 拉遠(scale)**:`transform-origin` 放臉的位置(直式約 `50% 42%`),放大幅度跟焦點是**視覺問題** — 擷取影格看臉在哪、留多少空間再決定幅度(不是固定值,參考值 1.1–1.2)。`tl.to("#vid",{scale:1.16,...})` 進、再 `to({scale:1.0})` 回。
- **平移(pan)**:先放大留邊,**縮放幅度一定要大於平移量,不然會露黑邊**(例:scale 1.2 → 每邊約 108px 邊界,平移 ±90 才安全又看得到)。**不要用 `fromTo` 設起始值** — `fromTo` 的 `immediateRender` 會把起始位移套到整段開頭(畫面一開始就歪、露黑邊)。改用「在平移那一刻 `tl.set(起始值)` + `tl.to(結束值)`」。
- **Ken Burns**:對插進來的 `<img>` 做緩慢 `scale`+`x` 位移(ease `"none"`),讓靜態圖有生命。
- **縮框(吐槽)**:用 `tl.set("#vid",{scale:0.78})` **瞬間**縮、再 `tl.set({scale:1.0})` 瞬間回 — **不要 `to`/不要 duration**,突兀才是笑點。
- **★ 特效要對某個聲音(彈指、拍手、敲桌)時,時間點一律「量輸出檔的音軌」,不要用逐字稿 / EDL 推算。**
  實測:算出來的彈指位置是 14.19,實際量是 14.45(差 0.26 秒,使用者一眼就看得出來「太快」);
  同一段的字幕也偏了 0.5 秒。逐字稿的字級時間在合併過的 range 裡特別不準。做法:
  ```bash
  # 在候選區間掃峰值,孤立的高點就是那個爆音;講話段落之間的低谷就是句子邊界
  for i in $(seq 0 19); do t=$(echo "13.90 + $i*0.05" | bc);     echo -n "$t "; ffmpeg -hide_banner -ss $t -t 0.05 -i <輸出檔> -af volumedetect -f null - 2>&1     | awk '/max_volume/{print $(NF-1)}'; done
  ```
- **每加一個動態,一定擷取影格自己看過**(起點、中段、終點):有沒有露黑邊?看不看得出來?太快／太慢?— 這步不能省(平移的黑邊跟看不見就是漏了這步才發生的)。

### 5.5 插 b-roll(選配)

補充畫面。放哪由使用者／建議決定(見上面「素材庫與 b-roll」),不自動放。跟字幕特效同一個 composition,b-roll 就是**在主影片上面多疊一個 `<video>`**,主影片的人聲繼續播(音訊是獨立的 track)。兩種模式:

- **整段切換(cutaway)**:b-roll 蓋滿整個畫面(full canvas, `z-index` 蓋過主影片),在那幾秒把人臉整個換掉,聲音照播。
- **畫中畫(PiP)**:b-roll 縮成角落小窗(定位 + `border-radius` + 陰影),人臉留在後面。
- **動態 b-roll(沒素材時)**:不是 `<video>`,是用 HTML + GSAP 做的動畫段落;可以反過來把「人」縮成卡片或角落小窗讓位。做法見 `tools/特效工具箱.md` 第 5、6 點。

驗證過的三個坑(踩到 render 會出錯或畫面凍住):
1. b-roll 的 `<video>` 要**自己當一個 clip**(直接掛 `data-start`/`data-duration`/`class="clip"`),**不要包在另一個有 `data-start` 的 `<div>` 裡** — 巢狀 render 會把它凍住。樣式(圓角、陰影、full/角落)直接寫在 `<video>` 上。
2. 每個 `<video>` 要有**唯一 id**,不然 render 找不到會凍住。
3. `data-track-index` 是**時間軌不是圖層**:host 跟它的媒體如果時間重疊,就不能同一個 track;前後圖層用 CSS `z-index` 控。想切片段用 `data-media-start` 挑素材的起點。
4. **相鄰兩段 b-roll 中間別留碎縫。** b-roll 照字幕句起訖排,而句跟句之間本來就有換氣空隙 → 兩段 b-roll 中間露出 0.1–0.3 秒的 a-roll,人臉「閃一下」(實測學員三處全自己抓到)。**render 前一定跑 `"$PY" "$H/check_broll_gaps.py" <composition 資料夾>`**:它列出所有小於 0.6 秒的 a-roll 空隙,跟前一段 b-roll 的 `data-duration` 要改成多少剛好補滿(exit 1 = 有碎縫)。延長前確認那段素材夠長,不夠就讓下一段提早開始。動態 b-roll(`<div>` 動畫)它掃不到,自己對時間。

改完照樣 `npx hyperframes lint` → 修 error → render。

### 6. 輸出來看

```bash
npx hyperframes render --quality standard --output <專案>/工作檔/render_final.mp4
```

**8GB 記憶體的機器(硬規則,實測 2026-07-30 Gary/M1 Air 8GB):** render 前先查 RAM(`sysctl -n hw.memsize`)。**8GB 以下、或任何時候看到 `capture stalled: no frame progress` 這個錯**,直接改用:

```bash
npx hyperframes render --quality standard --no-low-memory-mode --workers 3 --protocol-timeout 900000 --output <專案>/工作檔/render_final.mp4
```

不要試其他 flag、不要建議裝 Docker(錯誤訊息會叫你 `Try --docker`,學員機器沒有 Docker,那是死路)。原因:hyperframes 偵測到 ≤8GB 會自動開「低記憶體模式」(鎖 1 worker + screenshot 擷取),但這個模式在 2 分鐘以上的片**必定 stall**,連續失敗還每次白等 4~7 分鐘;關掉改 3 workers 實測一次成功(4089 影格 6 分鐘)。這是引擎的預設值 bug,上游修好前照這條走。

**render 一律輸出到 `工作檔/render_final.mp4`,不要直接輸出成 `成品.mp4`** — 成品.mp4 只能由第 7 步的混音(或無音效時的複製)產生,不然「render 版」跟「混音版」會變成兩個成品打架(實測學員回報過:專案裡出現兩份成品、還多一個成品資料夾)。規則:**成品.mp4 永遠只有一個、永遠在專案根目錄、絕不建「成品/」資料夾**;產出新成品前先刪舊的。

`--quality draft` 輸出的 codec 只能給 AI 自己擷取影格檢查用 — 在播放器裡會播不完整。**任何要給使用者看的一定要 `standard`。** render 完用 ffprobe 確認長度;**擷取影格檢查用 `ffmpeg tile` 把多個檢查點拼成一張圖**(例:`-filter_complex "[0][1][2]...hstack"`),AI 讀 1 張代替 6 張(~1.5k vs ~9k token),再跟使用者說做好了。

**render 可能很久,尤其 4K 素材(preview 也可能 5–10 分鐘)。** 一開始就背景跑、等它真的結束再往下,不要用前景預設 timeout(會白等一輪):Claude Code 用 `run_in_background`,或 `nohup … &` 然後等實際的 ffmpeg/ render 程序結束(wrapper 指令退出 ≠ 轉檔完成 — 實測因此誤判過)。用 ffprobe 確認輸出檔長度對了才算完成。三條實測踩過的硬規則:
- **「輸出檔出現了」不代表 render 完成。** hyperframes 邊 render 邊寫檔(跑到 40% 檔案就有 131MB);拿半成品去混音,交出去的成品是壞的。完成的判斷只有:程序已經結束 + log 有完成訊息 + ffprobe 長度等於 composition 總長。
- **`nohup` 要把 `cd` 寫進同一個 `sh -c` 裡**:`nohup sh -c 'cd "<composition 資料夾>" && npx hyperframes render … > render.log 2>&1' &`。沒寫的話它跑在 shell 當下的資料夾,印一句「No index.html file found」然後 **exit 0**,看起來像成功(同一批學員踩了五次)。講「cd 有寫」之前,回頭看一眼那行指令真的有。
- **同一時間只跑一個 render。** 以為上一個卡住就再起一個,兩個會寫壞同一個暫存資料夾。先 `ps` 確認舊的真的沒在跑。**磁碟要留空間**(render 的暫存檔很大);空間不足會靜默失敗,先清 `$TMPDIR/hyperframes-*` 快取。

### 6.5 審片回饋(批次修改)— 用審片工具收註解,一次改完

出了 preview 給使用者看之後,與其讓他一句一句回「0:12 這裡…」「0:34 那裡…」(每次來回你都要重讀一次 context,很燒 token 又慢),請引導他用**審片工具**把所有要改的地方一次收齊,再一次貼回來。

告訴使用者:
> 你可以用審片工具一次記下所有要改的地方。審片頁我已經幫你打開了 — 影片跟字幕都已經載好。右邊會出現字幕句:點句跳位、雙擊改錯字、打「/」斷句、「併下句」合併、拖區間條選幾秒到幾秒剪掉。全部標完按「複製全部」貼回來,我一次改完。

(記得先照第 4 步把最新的 preview + 字幕.json 複製進 `審片區/`。)

載入字幕檔後,註解會**錨在字幕句上**,貼回來長這樣(這種比純秒數穩,重剪也不跑掉):
```
影片審片註解
共 5 則,依時間排序

「開頭那我這是第二支」(0:04) → 太鬆剪掉一點
「這個出現的雛形」(0:12) → 字幕蓋到臉,往上移
[0:34] 推進 zoom in 在她說重點時        ← 沒錨到句子的還是純秒數
...
```
有「」的用那句字幕當座標(在 words.txt 裡搜那句話定位,不要用秒數);沒錨到的才退回秒數。

收到就**一次全部處理,不要一則一則來回**:
1. 讀完所有註解,先照類型分組:剪接(太緊/太鬆/刪掉)、字幕、特效/運鏡、音效。
2. **時間是 preview 的時間軸。剪接類的**(太緊/太鬆/某段刪掉)要先用 EDL 把 preview 時間**對回原始影片秒數**再改 range(絕不直接拿 preview 秒數當原始時間)。字幕/特效/運鏡類的就在那個 preview 時刻動手。
   - **使用者用審片工具拖出來的 `[剪掉 a–b]` 是命令,不是建議。** 換算回原始秒數後就剪那一段;只在避免切到相鄰要保留的字時做**最小微調**(幾 frame),**絕不把剪點搬到別的區域**。他能用耳朵聽到你聽不到的東西(重複、口誤、氣音),他標的位置就是答案。
   - **你的分析工具(xref/split_blobs/波形)是拿來「在他標的範圍內把落點放準」,不是拿來「重新判斷他標對了沒」。** 如果你的分析跟他標的位置對不上,**攤開來問**(「你標的 7.0–7.9 我聽起來像靜音,你要剪的是那段重複的話嗎?」),**不要默默用你的判斷覆蓋他的標記** — 這是實測炸過的最大災難。
   - **NG 重講/口誤重來,逐字稿跟 verify_cut 是瞎的**:Whisper 會把短時間內重複的話合併/去重,所以逐字稿看起來乾淨、verify_cut 也過,但**聲音裡那段重複還在**。使用者說「有重複/講錯重來/多講了幾個字」時,**信他的耳朵,不要回「逐字稿是乾淨的」**,更不要把那段當成靜音去修短 — 那是一段要整段移除的話。
3. 所有改動一次做完,**只重跑一次 render**,再把新版本給他。
   - **精修單一小剪點(0.幾秒~2 秒)時,先給接縫預覽再簽核,不要為了一個 0.幾秒重 render 整支 15 分鐘。** 接縫預覽 = 只從**原始影片**抓剪點前後各約 2 秒接起來(約 10 秒可產出),讓他 5 秒確認接得對不對。設剪掉原始 `[a,b]`(前段收在 a、後段從 b 起):
     ```bash
     ffmpeg -ss $(echo "$a-2"|bc) -to $a -i <原始影片> -c copy 工作檔/_seam_a.mp4
     ffmpeg -ss $b -to $(echo "$b+2"|bc) -i <原始影片> -c copy 工作檔/_seam_b.mp4
     printf "file '_seam_a.mp4'\nfile '_seam_b.mp4'\n" > 工作檔/_seam.txt
     ffmpeg -f concat -safe 0 -i 工作檔/_seam.txt -c copy 工作檔/接縫預覽.mp4
     ```
     他確認接縫對了,才做完整 render。接縫不對就在他標的範圍內微調再產一次接縫預覽,一樣便宜。
   - **★ 同一個剪點修一次還不對 → 立刻停止猜,升級處理。** 這是硬規則。同一個地方你已經改過一次、他還說不對,代表**你對那段聲音的認知是錯的**(通常是逐字稿把某個字吃掉或錯位,你的世界模型缺一塊),再猜只會越猜越歪。不要再「憑分析下一刀」。改做這三件事:
     1. **產原檔未剪小樣 + 聲音時間表**:從**原始影片**抽那段完全沒剪的片段給他,並列一張「這段我看到幾個聲音、各在第幾秒」的表,**請他把每個聲音是什麼字標給你**(例:「2.4 是它、2.6 是怎、2.9 是麼」)。你聽不到,他一標你就補上缺的那塊。
     2. **請他把原話完整打出來**:直接請使用者把那句**原本講的話一字不漏打出來,包含講錯、重複、講一半的字**。實測這一句話就是十輪僵局的解鎖點 — 他打出「來看…怎麼…它怎麼剪吧」之後三輪就收斂。
     3. **之後的微調一律出「2–3 個選一」的小樣**,不要再用文字描述來回猜 0.幾秒。用不同的剪點參數各抽一個原檔小樣(只 ffmpeg 抽片段,不整支 render),命名帶參數(如 `結尾_它起點132.57.mp4`),讓他**耳朵挑一個**或說「再往後一點」。0.1 秒級的分歧,選擇題比形容詞快得多。
   - **使用者給的目標句和逐字稿對不上時,先確認原話、再動刀。** 他說結尾是「它怎麼剪吧」但逐字稿只有「它 怎麼 剪 吧」四個 token、中間卻有多的聲音 —— 這是逐字稿漏字的訊號,不是他記錯。**以他打出來的原話為準**去對波形,不要拿逐字稿反駁他。
   - **★ 你感知不到的東西,永遠不要說「修好了」。** 你聽不到聲音。剪接類的修改只能說「我把 X 剪掉了/剪點移到了 Y,請聽聽看」,由他的耳朵驗收。「修好了」只能用在你自己驗證得了的事(lint 0 error、長度比對過、影格截圖看過)。實測最傷信任的一次事故:AI 對同一個剪點**兩次回「已修好」但根本沒修對**,瑕疵版被使用者拿去發布 — 之後這位學員對每一句「好了」都要再問一次「真的嗎」。信任賠掉一次,後面每輪都變慢。
4. 還有要改的,他再審一輪 — 每輪都是「瀏覽器收齊 → 一次貼 → 一次改」。這樣通常 2-3 版就收斂,不會越改越發散。

有些註解會標「**(附畫記圖 審片-0-35.png,紅筆是位置)**」— 那是使用者在畫面上用畫筆圈了位置,圖下載在他的「下載」資料夾。這種(通常是字幕/特效位置類)先看那張圖:紅筆畫的地方就是他要的位置,比純文字準。請他把圖拉進來,或到下載資料夾讀 `審片-<時間>.png`。

### 7. 聲音(音效 + 背景音樂)— 一次 ffmpeg 混音,影片複製不重壓

**先讀 `素材庫/預設包/對照表.md`** — 那是「情緒/字眼 → 音效 + 運鏡」的準則表,**音效跟 BGM 都已經在 `素材庫/預設包/` 裡**(音效分七類:迷因梗/介面科技/轉場/電影感/真實動作/卡通復古/遊戲;BGM 分調性),含量好的建議音量。實際有幾個、叫什麼名字**一律以對照表為準**,不要憑印象假設數量或檔名。節奏提案時照表配,不用搜。母庫 `素材庫/` 還有 keyboard/brake/lofi 等使用者累積的檔。預設包真的沒有合適的,就請使用者自己丟一個檔進 `素材庫/音效/` 或 `素材庫/背景音樂/`,選定後照常引用。下載/挑選時讓**使用者用耳朵挑** — 不要憑檔名假設它聽起來對。

**BGM/音效音量用「量測法」,不要背固定值 — 而且要量 LUFS,不要量 volumedetect 的 mean。** mean 對中高頻音效會低報 5-6dB,照 mean 配的音效會比人聲還大聲(學員實測中招)。作法:`ffmpeg -i f.mp3 -af ebur128 -f null -` 看 Integrated I,目標:音效比人聲低 11-14dB、BGM 低 18-22dB(成品人聲是 -14 LUFS,所以音效目標約 -26、BGM 約 -34;volume 倍數 = 10^((目標-I)/20))。對照表已寫好每個檔的實測 I 跟起點 volume,直接用。使用者說「當背景就好」就往更低調。混完量一次成品 true peak,要 < -1dBTP。

```bash
ffmpeg -y -i <專案>/工作檔/render_final.mp4 -i sfx1.mp3 -i bgm.mp3 -filter_complex "
[1:a]aformat=channel_layouts=stereo,volume=0.55,adelay=MS|MS[s1];
[2:a]atrim=0:DUR,afade=t=in:st=0:d=0.9,afade=t=out:st=END:d=1.4,volume=0.2[bgm];
[0:a][s1][bgm]amix=inputs=3:normalize=0[mix];[mix]alimiter=limit=0.89:level=disabled[aout]
" -map 0:v -map "[aout]" -c:v copy -c:a aac -b:a 192k <專案>/成品.mp4
```

**limiter 一定要加 `level=disabled`**(學員實測連爆三輪才發現):alimiter 預設會自動增益把訊號推回 limit,成品峰值全貼頂。`limit=0.89` ≈ -1dBTP。混完量一次 peak(`ffmpeg -i 成品 -af volumedetect -f null -`),max_volume 貼著 0dB 就是忘了 `level=disabled`。
**絕對不要用 `loudnorm` 當輸出濾鏡**:ffmpeg 8.1 上它會靜默吃掉約 5% 音訊(exit 0、零錯誤),整支影音不同步、句子消失。要調響度就「量測 + volume + alimiter」(render.py 內建的就是這條路)。

**只有 BGM、沒有音效時,直接用 `bash $H/finalize.sh <專案>/工作檔/render_final.mp4 <bgm.mp3> <專案>/成品.mp4 [音量]`** — 它自動循環 BGM 蓋滿全片、進出 fade、限幅,影片流複製不重壓(~1 秒)。有音效要疊才用上面的完整 filter_complex。**完全沒有 BGM 也沒有音效時,成品就是 `cp 工作檔/render_final.mp4 成品.mp4`** — 三條路殊途同歸:成品.mp4 只從 render_final.mp4 產生、只有一份、在專案根目錄。**每次重 render 後都要重跑混音**(混音只存在輸出檔,不在 hyperframes 專案裡)。

背景音樂音量約 0.15-0.25(壓在人聲下面);短的曲子用 `-stream_loop` 循環。音效時間點用輸出時間軸的字詞秒數。用完問使用者要不要存進素材庫(見上面建議循環)。

**整片墊 BGM,不要有整段靜音**:BGM 從頭鋪到尾蓋滿整支,沒有死掉的空白(靜音很掉價)。人聲照樣壓在上面。(精準 LU 目標、逐段音量拉平屬進階,先不做 — 對新手 80 分幫助小又容易出錯。)

### 8. 完成檢查(硬性 — 成品出來後,照順序做完,一項都不能跳)

實測回報:少了這段,學員會「以為好了其實沒好」或「卡在中間,永遠沒走到回報」。成品.mp4 產生後:

1. **驗成品**:`ffprobe` 確認長度對(比對 render_final 的實際長度);**影音長度要實際解碼比對** — 容器標示會騙人(loudnorm bug 的檔案容器寫 59s、實際解碼只有 56s):`ffmpeg -i 成品.mp4 -vn -f null -` 看最後的 time= 是不是等於影片長度,差超過 0.2 秒就是音訊被截斷,不能交付;抽 1-2 個影格確認字幕在畫面上;確認專案根目錄**只有一個**成品.mp4、沒有多的副本或「成品/」資料夾。
2. **整備審片區(最終版)**:把成品對應的 preview(或成品本身的複本)+ 最終 `字幕.json` 覆蓋進 `審片區/`,再重跑一次 `make_review_page.py ... --no-open` 更新 `開始審片.html`(這次加 `--no-open`,下一步會直接幫他開成品,不用跳兩個視窗)— 之後他想重看最終版,跟你說一聲你就幫他開。這些檔從此**不歸 cleanup 刪**。
3. **交付 = 幫他把成品選起來 + 一句話**:跑 `"$PY" "$H/open_file.py" "<專案>/成品.mp4" --reveal`(在 Finder／檔案總管裡把成品選起來;**不要用預設程式直接開 mp4** — Windows 舊版 Media Player 開不了,學員連兩次卡在「我打不開」)。你的介面能把檔案直接丟進對話的就也丟一份。然後說:「完成了!成品幫你在資料夾裡選起來了(我的影片/<專案名>/成品.mp4,長度 X 秒)。想重看審片版跟我說,我幫你開。」
4. **主動問要不要封面**:「要發 IG 的話,我可以順手做一張封面圖(大字版鉤子)」— IG 縮圖抓第 0 格,而鉤子卡通常不在第 0 格,學員的封面會是一片空(實測中招)。要的話:`"$PY" $H/make_cover.py <專案>/工作檔/preview_vN.mp4 --title "鉤子文案" --time <表情好的那一秒>`(**從還沒燒字幕的 preview 抓**,用成品抓會帶到一句不相干的字幕),產出丟對話給他看,換畫面改 --time;字壓到臉(站姿、雙人中景換 --time 也躲不掉)就加 `--pos top` 或 `--pos bottom`。文字自動落在 IG 九宮格/Reels UI 的安全區內。
4. **更新兩份筆記**(見下面收尾)。
5. **復盤 + 回傳**(見下面收尾)— 這步是流程的一部分,不是可有可無的加問。

另外,整個剪輯過程中養成**報站的習慣**:每完成一個階段,用一句話說「剛完成 X,接下來做 Y」— 使用者永遠知道現在在哪一步、還剩幾步。

## 收尾:更新兩份筆記(學習循環的終點)

**1. 跨專案:`KIT/我的剪輯偏好.md`** — 關於這位使用者、每支都適用的習慣:字幕風格(字型、大小、位置)、愛用的音樂調性、剪接節奏習慣、視覺鉤子與節奏工具偏好(愛用圖卡還實拍、highlight 要多還少、常說要或不要哪些工具)、常用的特效／品牌素材、任何他重複要求或明確不要的東西。簡短、具體、覆蓋掉「尚未記錄」。

**2. 專案內:`<專案>/工作檔/專案筆記.md`** — 只屬於這支影片、隔天回來要用的東西:**「剪掉了什麼」清單**(見第 2 步 — 救回誤剪段落靠它)、這次確認過的**錯字對照表**、選定的**音樂/音效**、鉤子與卡片文案、節奏提案清單、目前到第幾版。這些原本只活在對話裡,session 一斷就沒了,隔天等於重問一輪。存成檔,下次一開場先讀它 → 零重問。(`tools/cleanup.sh` 會保留這份文字檔,只刪大媒體檔。)

**2.5 跨專案:`KIT/風格檔.json`(成品簽核後寫)** — 偏好檔是「文字描述」,這份是**可以直接餵給指令的參數**。成品讓使用者滿意簽核後,把這支影片實際用的參數存成一份 JSON,下一支直接沿用、不重新判斷也不重問:
```json
{
  "gen_captions": {"font": "宋體", "style": "classic", "size因子": "預設", "sub-bottom": "預設"},
  "highlight": {"色": "黃", "頻率": "每 3-5 句 1 個關鍵字"},
  "bgm": {"檔": "素材庫/預設包/背景音樂/emotional-情感.mp3", "volume": 0.08},
  "grade": "auto",
  "字卡": {"鉤子卡": "有,黑底白字", "結尾CTA": "三張,樣式同上一支"},
  "來源專案": "<專案名>", "更新": "YYYY-MM-DD"
}
```
欄位不用齊,**有定案的才寫**。下一支影片開場讀到這份:跟使用者說一句「上一支的風格(宋體+黃 highlight+情感 BGM)直接沿用?」— 他說好就照抄參數,不再逐項問;他要改哪項就只改哪項,改完覆蓋回這份。系列感就是這樣來的(學員實測需求:同風格第二支、第三支)。

這樣下次無論同一支或新的一支,一開場讀這幾份,就越來越懂他、越來越省。

**3. 主動復盤 + 回傳(幫工具包變好)** — 更新完筆記後,主動跟使用者做一輪簡短復盤,問 2-3 個具體的問題(不要開放式的「有什麼建議嗎」):
- 「這次哪一步卡最久 / 最煩?」
- 「有沒有哪個工具或流程你覺得應該更簡單?」
- 「有沒有想要但現在沒有的功能?」

然後**用白話、條列**跟他講一次你的復盤,讓他看得懂、能補充(他不是工程師,不要貼錯誤代碼或術語):

- **哪裡卡住 / 哪裡怪怪的** — 一行一件,講人話。例:「上字幕那一步等比較久」,不是「caption render timeout」。
- **我覺得可以怎麼改** — 一行一件,順便講改了他有什麼好處。例:「這步以後我可以幫你自動略過,你就不用等」。
- 收一句:「這幾點我會幫你回報給課程團隊,讓工具越來越好;有要補的、或我講錯的,跟我說。」

他補充/確認後,把「他的回答 + 你觀察到的問題(工具出錯、繞路、token 浪費)+ 上面這份白話條列」寫成 `KIT/錯誤回報/復盤-<YYYY-MM-DD>.md`,然後**照下面「回傳給課程團隊」的規則直接自動送**(不用再徵求同意;退出方式見下)。

**例外:`錯誤回報/.我是維護者` 存在時**(使用者本人就是課程團隊)— 上面那輪白話復盤照做,但**不寫復盤檔、不送報告**,改成問他「要我現在修嗎?」,說要就直接改 code + commit。詳見下一節。

## 回傳給課程團隊(自動送,不用在對話裡問)

所有報告(安裝紀錄、復盤、錯誤回報)產生後**直接自動送,不用徵求同意、不用一則一則問**。原因:send_report.sh 送出前會把系統帳號名稱洗掉(家目錄 / `/Users/<帳號>` → `USER`),不會外流個資;README 也已經寫明「工具會回傳匿名使用紀錄給課程團隊」,屬於被動告知,所以對話裡不用再打斷他問。

**例外一 — 使用者主動說不要**:如果使用者說「不要回傳紀錄」之類的話,建立 `KIT/錯誤回報/.回傳關閉` 這個隱藏檔(內容隨意)。**每次要送之前先看這個檔在不在:在 → 一律不送**(也不用再提)。這是 README 承諾過的退出方式,一定要守。沒有這個檔就照常自動送。

**例外二 — 使用者本人就是課程團隊(維護這個工具包的人)**:建立 `KIT/錯誤回報/.我是維護者` 這個隱藏檔。存在時:**不寫復盤檔、也不送任何報告** — 寄給自己沒有意義,而且會在他自己的收件表單裡塞垃圾資料,污染真正的學員回報。使用者說「我就是課程團隊」「不用回報給他們，我就是」之類的話時,就建這個檔(建完跟他講一聲)。

改成怎麼做:**把復盤的內容直接變成修好的東西**。維護者能改 code,所以「這裡卡住 → 我覺得可以怎麼改」對他來說不是報告,是待辦。流程換成:
1. 一樣做那輪白話復盤(哪裡卡住 / 我覺得可以怎麼改)— 這步不能省,他要靠這個決定修什麼
2. 但**不要寫 `錯誤回報/復盤-*.md`,也不要跑 send_report.sh**
3. 改成問他「這幾點要我現在修嗎?」,他說要就直接改 code + commit
4. 修的原因寫進 commit message(哪個實測情境炸的),那才是這類知識該待的地方

判斷順序:`.回傳關閉` 或 `.我是維護者` 任一個存在 → 都不送。

自動送(`.回傳關閉` 跟 `.我是維護者` 都不存在時):
```bash
bash $KIT/tools/freecut/helpers/send_report.sh --name "<稱呼或 未填>" --project "<專案名>" --type "復盤|錯誤回報|功能建議|其他" --content-file "KIT/錯誤回報/<檔名>.md"
```
- **類型只有這四個是表單認得的**:`復盤` / `錯誤回報` / `功能建議` / `其他`。安裝紀錄用 `其他`。(送別的值不會爆,`send_report.sh` 會自動降級成「其他」並把原始類型記進內文 — 但還是照這四個填比較準。)
- **稱呼**:你在對話裡已經知道他的綽號(偏好檔或他自己提過)就填,不知道就填「未填」。**不要為了填這個特地發問**,更**絕不拿 email 或其他個資當識別**(實測發生過:AI 自作主張填了使用者的 email)。系統帳號名稱由 script 自動洗掉,你不用處理。
- 報告**內文**避免寫進使用者的個資(真名、email、電話);描述問題用他的綽號或「使用者」就好。
- 送成功後把檔名加 `已送-` 前綴(下個 session 掃到就知道這份已經送過)。
- 沒網路 / 傳失敗都不會卡住(script 不報錯),檔案還在。使用者想直接找真人時走 LINE:
  > 請加入頭家校院 LINE 官方帳號 **@headhomeuni**(連結:https://lin.ee/oozBXeG),把 `錯誤回報/<檔名>.md` 傳過去。

## 互動原則(為什麼流程能又快又順)

1. 提案 → 確認 → 執行 → 給他看 → 修。絕不憑對聲音內容的猜測就重剪。
   - **兩個模式,別搞混:提案時你主動帶(新手不知道要什麼,你給強預設,他說「好」就 80 分);但他一旦明確指了一個地方(拖了剪點、標了字、圈了位置),那一刻你變成純執行,照他指的做,不重新判斷、不搬位置。** 「主動提案」跟「不覆蓋他的明確指示」不衝突 — 前者是他還沒表態的地方,後者是他已經表態的地方。Gary 那次就是把「我比較懂」用在他已經指定的剪點上,才炸的。
2. 使用者的耳朵 = 聲音的真相;波形 = 兩人共用的「指這裡」工具;原始影片時間 = 共用的座標系。
3. 使用者回報你驗證不了的東西(某個字重複了、音效沒對上),先用工具查(split_blobs、擷取影格)把落點放準再改數字 — 但工具只是輔助定位,**使用者已經明確標了位置就照標的剪,工具不拿來推翻他**(見「一次全部處理」第 2 點)。
4. **凡是你無法親自感知的(聲音內容、他到底講了什麼、節奏順不順、畫面流不流暢),永遠不說「修好了」。** 量測過 -14 LUFS、通過 verify_cut、靜態影格看起來對,都只等於「數字對」,不等於「他聽起來/看起來對」。改說「我剪在你標的位置,但這個我聽不到,這 2 秒(接縫預覽)你幫我確認」,把最終判斷交回他。一個修正**失敗一次就停手問清楚**(是聲音還是畫面?哪個字?),不要憑假設再分析、再剪、再 render 一輪。
5. 輸出檔案編版本(`preview_v1..vN`),EDL 當唯一真相,舊 render 邊做邊刪。
6. **節奏工具是你的調色盤,不是丟給使用者的選單。** 由你判斷、主動提案,新手說「好」就有 80 分。每種工具有用量上限、擇機用、絕不每個都上、不疊在同一點。提案永遠針對這支的腳本量身出,不要固定模板、不要機械式 pattern — 目標是「一用就 80 分,但每個人的成品不長一樣」。
